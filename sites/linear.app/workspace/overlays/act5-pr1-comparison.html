What each source contributes

The two sources operate at different altitudes. ACT-5 is a design brief and philosophy of operation. PR #1 is an implementation-shaped schema draft. The right workflow should not pick one over the other; it should use ACT-5 as evaluation criteria and PR #1 as the first executable grammar.

ACT-5 contributes the design constraints

  • Model websites as maps of where function exists on DOM surfaces.
  • Represent context-dependent availability and state traversal.
  • Separate agent-initiated targets from UI-originated signals.
  • Make files composable across website, local, and third-party sources.
  • Test schemas against the living site and plan for drift.
  • Clarify how runtimes translate entries into OpenAI Responses semantics.

PR #1 contributes the first portable vocabulary

  • protocol, version, surface, prompt, tools, and signals.
  • x_actions as vendor-neutral bridge metadata.
  • Safe dotted identifiers for tools, handlers, and events.
  • Input, result, and payload schemas with validation rules.
  • Source hints: files, symbols, selectors, and components.
  • Runtime errors for invalid input, missing handlers, timeouts, and invalid results.

Ideal user workflow

A user bringing ACT-5 and PR #1 together should move from evidence to schema changes to live verification. The goal is not just a prettier doc; it is a repeatable review loop for each schema revision.

Collect evidence

Open the Linear issue, PR, and example manifests. Extract claims into a shared comparison table with source links and exact file references.

Translate principles

Turn ACT-5 statements into acceptance criteria: state traversal, composability, deterministic execution, testing, and protocol mapping.

Score the proposal

Evaluate each PR #1 field against those criteria. Mark coverage as strong, partial, or gap, with a concrete schema change for every gap.

Draft schema deltas

Add minimal extensions rather than rewriting the draft: states, imports, checks, and Responses bindings should layer onto PR #1.

Test on real pages

Use simple-form first, then Linear-like onboarding flows. Validate selectors, state transitions, handler resolution, and expected results.

Record drift handling

For each failed probe, capture what changed and whether the action can recover through alternative selectors, transition paths, or user handoff.

Publish a focused PR

Keep PR #1 as the base proposal, then open a follow-up PR that adds the missing model layers and examples.

Repeat per surface

Run the same loop on Kanban, chess, slide deck, and live SaaS forms until the schema survives multiple interaction styles.

Concrete schema deltas

These are not final syntax decisions. They are sketches of the minimum vocabulary needed to satisfy ACT-5 without losing PR #1's current shape.

State traversal layer

Describe where targets are available and how to reveal them.

{
  "states": [
    {
      "name": "workspace.create",
      "detect": {
        "selectors": ["input#name", "button[type='submit']"]
      },
      "targets": ["workspace.fill_name", "workspace.create"]
    }
  ],
  "transitions": [
    {
      "name": "open.region_menu",
      "from": "workspace.create",
      "to": "workspace.region_menu",
      "action": "region.open",
      "reveals": ["region.select"]
    }
  ]
}

Composable source layer

Make website, local, and third-party maps explicit.

{
  "imports": [
    {
      "namespace": "linear",
      "source": "https://linear.app/actions.json",
      "trust": "site"
    },
    {
      "namespace": "team",
      "source": "./actions.local.json",
      "trust": "user"
    }
  ],
  "conflicts": {
    "strategy": "namespace_required"
  }
}

Live check layer

Let validators compare the map against the living page.

{
  "checks": [
    {
      "name": "workspace_name_available",
      "setup": ["state.workspace.create"],
      "assert": [
        { "selector": "input#name", "visible": true },
        { "tool": "workspace.fill_name", "input": { "name": "test" } }
      ],
      "on_failure": "schema_drift"
    }
  ]
}

Responses binding layer

Define exact transport semantics for tools and signals.

{
  "protocol_bindings": {
    "openai.responses": {
      "tool_call_item": "actions.call",
      "tool_result_item": "actions.result",
      "signal_item": "actions.signal",
      "correlation": "call_id",
      "errors": "structured"
    }
  }
}

Recommended path forward

The most useful next move is a follow-up PR that treats PR #1 as the base vocabulary and adds ACT-5's missing operational layers through examples and validation rules.

Keep PR #1

Do not discard the current proposal. Its tools[], signals[], x_actions, and source hints are the right portable core.

Add an ACT-5 appendix

Convert the Linear principles into a formal acceptance checklist inside the schema docs, so future PRs are judged consistently.

Open PR #2 for model layers

Add state traversal, imports, checks, contingencies, and Responses bindings with one small example for each.

Update simple-form

Keep the handler path, but add an optional deterministic trace or check so the example demonstrates more than handler dispatch.

Validate on a live form

Use the Linear workspace setup flow as a real-world test bed for input fields, derived slugs, dropdown state, submission, and handoff boundaries.

Working thesis: PR #1 should become the catalog layer of actions.json. ACT-5 should become the evaluation layer and the roadmap for schema depth. The combined standard should answer four questions for every action: where is it, when is it available, how is it executed, and how do we know it still works?
