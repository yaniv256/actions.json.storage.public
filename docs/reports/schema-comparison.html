What each source contributes

The two sources operate at different altitudes. The design brief provides goals and operating principles. The schema draft provides implementation-shaped vocabulary. The right workflow should not pick one over the other; it should use the design brief as evaluation criteria and the schema draft as the first executable grammar.

The design brief contributes the design constraints

  • Model websites as maps of where function exists on DOM surfaces.
  • Represent context-dependent availability and state traversal.
  • Separate agent-initiated targets from UI-originated signals.
  • Make files composable across website, local, and third-party sources.
  • Test schemas against the living site and plan for drift.
  • Clarify how runtimes translate entries into OpenAI Responses semantics.

The schema draft contributes the first portable vocabulary

  • protocol, version, surface, prompt, tools, and signals.
  • x_actions as vendor-neutral bridge metadata.
  • Safe dotted identifiers for tools, handlers, and events.
  • Input, result, and payload schemas with validation rules.
  • Source hints: files, symbols, selectors, and components.
  • Runtime errors for invalid input, missing handlers, timeouts, and invalid results.

Prototype evidence: Prime Video carousel

The Amazon Prime Video Continue Watching prototype is the clearest evidence that the schema draft needs a state-machine layer. The private storage record was reviewed for schema lessons only; this public report does not publish the user's watched titles, detail URLs, or item index.

What the prototype proved

  • The carousel was not a static list. It exposed a changing visible slice of cards.
  • The agent needed diagnostics for visible cards, stable detail URLs, cover URLs, and whether new cards appeared.
  • Cover image URLs were not all available up front; some appeared only after a card entered the active carousel state.
  • A failed left-side click strategy had to be corrected to horizontal scroll gestures.
  • Scroll transitions needed an explicit rate limit of at least one second between movements.
  • Completion required convergence: stop only after allowed scrolls no longer revealed new stable card identities.

What this means for the schema draft

  • tools[] can name prime_video.continue_watching.collect, but the tool catalog alone cannot explain when the action is complete.
  • source.selectors can point to links and images, but selectors alone cannot model a scroll-revealed state.
  • x_actions.handler can delegate execution, but reviewers still need inspectable diagnostics and transitions.
  • prompt.state_summary is useful prose, but the runtime needs structured states[], transitions[], preconditions, rate_limit_ms, and reveals.
  • The storage run log became part of schema design: failed attempts, user corrections, extraction lessons, and convergence criteria all informed the next action map.
Schema consequence The schema draft should remain the callable catalog layer, but the next revision should add a live-surface operation layer: state detection, transition methods, rate limits, reveal semantics, result merging, and stop conditions. Without those fields, a future agent can know what action exists but not how to operate the page until the desired collection is actually complete.

Ideal user workflow

A user bringing the schema design brief and schema draft together should move from evidence to schema changes to live verification. The goal is not just a prettier doc; it is a repeatable review loop for each schema revision.

Collect evidence

Open the planning notes, schema draft, and example manifests. Extract claims into a shared comparison table with source links and exact file references.

Translate principles

Turn the design brief statements into acceptance criteria: state traversal, composability, deterministic execution, testing, and protocol mapping.

Score the proposal

Evaluate each field in the schema draft against those criteria. Mark coverage as strong, partial, or gap, with a concrete schema change for every gap.

Draft schema deltas

Add minimal extensions rather than rewriting the draft: states, imports, checks, and Responses bindings should layer onto the schema draft.

Test on real pages

Use simple-form first, then Linear-like onboarding flows. Validate selectors, state transitions, handler resolution, and expected results.

Record drift handling

For each failed probe, capture what changed and whether the action can recover through alternative selectors, transition paths, or user handoff.

Publish a focused proposal

Keep the schema draft as the base proposal, then open a follow-up proposal that adds the missing model layers and examples.

Repeat per surface

Run the same loop on Kanban, chess, slide deck, and live SaaS forms until the schema survives multiple interaction styles.

Concrete schema deltas

These are not final syntax decisions. They are sketches of the minimum vocabulary needed to satisfy the design brief without losing schema draft's current shape.

State traversal layer

Describe where targets are available and how to reveal them.

{
  "states": [
    {
      "name": "workspace.create",
      "detect": {
        "selectors": ["input#name", "button[type='submit']"]
      },
      "targets": ["workspace.fill_name", "workspace.create"]
    }
  ],
  "transitions": [
    {
      "name": "open.region_menu",
      "from": "workspace.create",
      "to": "workspace.region_menu",
      "action": "region.open",
      "reveals": ["region.select"]
    }
  ]
}

Composable source layer

Make website, local, and third-party maps explicit.

{
  "imports": [
    {
      "namespace": "linear",
      "source": "https://linear.app/actions.json",
      "trust": "site"
    },
    {
      "namespace": "team",
      "source": "./actions.local.json",
      "trust": "user"
    }
  ],
  "conflicts": {
    "strategy": "namespace_required"
  }
}

Live check layer

Let validators compare the map against the living page.

{
  "checks": [
    {
      "name": "workspace_name_available",
      "setup": ["state.workspace.create"],
      "assert": [
        { "selector": "input#name", "visible": true },
        { "tool": "workspace.fill_name", "input": { "name": "test" } }
      ],
      "on_failure": "schema_drift"
    }
  ]
}

Recommended path forward

The most useful next move is a follow-up proposal that treats the schema draft as the base vocabulary and adds the design brief's missing operational layers through examples and validation rules.

Keep the schema draft

Do not discard the current proposal. Its tools[], signals[], x_actions, and source hints are the right portable core.

Add an acceptance checklist

Convert the design principles into a formal acceptance checklist inside the schema docs, so future changes are judged consistently.

Open a model-layer follow-up

Add state traversal, imports, checks, contingencies, and Responses bindings with one small example for each.

Update simple-form

Keep the handler path, but add an optional deterministic trace or check so the example demonstrates more than handler dispatch.

Validate on a live form

Use the Linear workspace setup flow as a real-world test bed for input fields, derived slugs, dropdown state, submission, and handoff boundaries.

Working thesis: The schema draft should become the catalog layer of actions.json. The design brief should become the evaluation layer and the roadmap for schema depth. The combined standard should answer four questions for every action: where is it, when is it available, how is it executed, and how do we know it still works?
